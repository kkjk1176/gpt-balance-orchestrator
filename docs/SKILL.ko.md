# 기능 작업 흐름 오케스트레이터

이 워크플로는 신뢰도나 처리량을 높일 때에만 적용하세요. 읽기 전용 작업, 명백히 사소하고 격리된 편집, 또는 다른 절차를 명시적으로 요청한 사용자 요청에 억지로 적용하지 마세요. 기능 단위는 테스트 가능한 완료 기준을 갖는 하나의 응집된 동작으로 취급하며, 단순히 파일, 클래스, 개별 메서드별로 나누지 마세요.

## 1. 작업의 형태 잡기

1. 적용 가능한 저장소 지침을 읽고 관련 코드와 테스트를 살펴봅니다.
2. 완료 기준, 영향 범위, 테스트 명령, 위험 요소를 명시합니다.
3. 변경을 독립적으로 구현하고 검토할 수 있는 가장 작은 **응집된 기능 단위**로 나눕니다. 동일한 동작 맥락이 필요한 부분은 하나의 단위로 유지합니다.
4. 의존성과 path 소유권 지도를 만듭니다. 쓰기 path와 동작 계약이 겹치지 않을 때에만 단위를 병렬로 실행합니다. 그렇지 않으면 의존성 순서대로 실행합니다.
5. 모든 단위와 의미 있는 위임 하위 작업에 [Routing](#routing)의 route를 배정합니다. 목적이 겹치면 더 높은 위험도 route를 선택합니다.

환경이 하위 에이전트 위임을 제공한다면 기능 단위에는 하위 에이전트 세션을 사용하세요. 각 세션에 목표, 승인 테스트, 소유 path, 금지·인접 path, 의존성, 검증 명령, 배정된 route, 명명된 완료 보고 채널을 포함한 범위가 정해진 브리프를 제공합니다. 위임 전에 채널을 선택합니다. 자동 최종 결과 전달, 명시적인 부모 메시지·보고 operation, 또는 부모 측 wait/status/read operation 중 하나입니다. 채널을 정하지 않은 “보고해줘” 요청은 완료 계약이 아닙니다. 공유 작업 공간에서는 겹치는 쓰기 작업을 동시에 위임하지 마세요. 별도의 사용자 소유 작업이 명시적인 사용자 요청에서만 가능하다면, 사용자 소유 작업을 새로 만들지 말고 하위 에이전트를 사용하세요.

## 위임 수명 주기

위임은 방치하는 전달이 아니라 부모가 소유하는 수명 주기로 다룹니다. 기본 완료 방식으로는 하위 에이전트에서 부모로 보내는 최종 보고를 사용하고, 능동적인 상태 추적은 예외일 때만 사용합니다. 위임 전에 완료 보고 채널과 채널 장애 시의 회수 동작을 선택하고 기록합니다. 에이전트를 생성한 쪽은 하위 에이전트의 최종 결과를 평가할 책임이 있으며, 명명된 채널을 통해 부모가 보고를 실제로 확인하거나 설명된 차단 사유를 받기 전에는 작업을 완료로 간주해서는 안 됩니다.

- **주 세션:** 전체 계획과 위임된 모든 작업 흐름을 소유합니다. 각 작업 흐름에 대해 소유자, 기대 결과, 의존성 또는 위험 수준, 명명된 완료 보고 채널, 회수 동작, 지연된 보고가 조치가 필요한 상태가 되는 조건을 가볍게 유지합니다. 하위 에이전트의 보고를 기다리는 동안 통합 작업을 계속하되, 정상 동작 중인 하위 에이전트를 계속 폴링하지 않습니다. 최종 보고는 주 세션이 자동 전달을 확인하거나 명명된 채널을 통해 회수했을 때에만 유효합니다. 필요한 최종 보고가 없는 상태에서 사용자 요청을 완료하거나 완료되었다고 보고하지 않습니다. 보고된 결과를 통합하고, 의존성과 충돌을 해결하며, 통합된 결과를 전달합니다.
- **하위 세션:** 배정된 범위의 작업을 완료하며 겹치지 않는 하위 작업을 위임할 수 있습니다. 해당 하위 작업을 완료로 취급하기 전에 위임한 각 하위 에이전트의 최종 보고를 받아야 하지만, 정상 동작 중에는 계속 폴링하지 않습니다. 보고를 반영하고 배정된 검증을 실행한 뒤, 종료 전에 명명된 완료 보고 채널을 통해 간결한 최종 보고를 제출합니다. 결과, 변경 path, 실행한 검사, 해결되지 않은 위험, 차단된 작업을 포함합니다. 채널이 실패하거나 사용할 수 없다면 조용히 종료하지 말고, 사용할 수 있는 가장 가까운 부모 보고 채널을 통해 해당 차단 사유를 보고합니다.
- **하위 에이전트:** 배정된 범위를 완료하고 가능하면 필요한 검증을 실행하며, 종료 전에 명명된 완료 보고 채널을 통해 최종 결과를 제출합니다. 부분 작업 후 조용히 멈추지 말고 차단 요인, 실패한 검사, 남은 작업, 보고 채널 실패를 사용할 수 있는 가장 가까운 부모 보고 채널을 통해 명시적으로 보고합니다.

하위 에이전트의 예상 보고 시점이 지났거나, 실패 또는 차단 신호를 냈거나, 상위 의존성이 답을 필요로 하거나, 작업 위험이 높을 때에만 상태를 적극적으로 확인합니다. 무제한 대기 대신 범위가 제한된 상태 대기를 사용합니다. 예상한 보고가 없으면 기록해 둔 회수 동작을 실행하여 최종 결과를 가져오거나 보고 채널 실패를 확인합니다. 하위 에이전트가 차단되거나 실패하거나 불완전한 결과를 반환하면, 부모가 책임을 유지합니다. 즉, 명확히 하고, 재시도하고, route를 변경하거나, 완료하기 전에 상위 단계로 올립니다. 위임된 하위 트리에서 평가된 최종 보고를 부모가 모두 확인했거나, 더 이상 진행할 수 없는 명확하고 사용자에게 보이는 차단 사유가 있을 때에만 상위에 보고합니다.

## 2. 각 기능 단위 구현하기

각 단위에 대해 다음 루프를 순서대로 사용합니다.

1. **Red:** 완료 기준을 표현하는 가장 작고 의미 있는 자동화 테스트를 추가하거나 업데이트한 뒤, 실행하여 의도한 실패를 확인합니다. Red 테스트를 만들 수 없는 경우(예: 외부 시스템만 관련된 변경)에는 이유를 설명하고 가장 가까운 실행형 검사를 사용합니다.
2. **Green:** 테스트를 만족하는 데 필요한 만큼만 프로덕션 코드를 구현하고, 집중 테스트를 실행합니다.
3. **Refactor:** 관련 테스트가 계속 통과하는 동안에만 설계를 개선하고, 집중 테스트를 다시 실행합니다.
4. **Review:** 독립적인 route의 비평가 또는 테스트 검토자가 diff, 완료 기준, 회귀, 경계 사례, 테스트 품질을 살펴보게 합니다. 구현자의 자체 확인을 필수 검토로 간주하지 마세요.
5. **Improve:** 검토 수정 사항이 범위가 분명하고 제한적이면 실행자 작업으로 배정하고, 그렇지 않으면 상향된 route를 사용합니다. 집중 테스트를 다시 실행하고, 수정이 동작을 크게 바꿨다면 검토를 반복합니다.

테스트 설계, 범위가 제한된 구현, 실패 분류, 집중 검토처럼 결과와 소유 path가 명확할 때에만 하위 작업을 위임합니다. 여러 단위 간 조율, 병합 결정, 위험 수용은 부모가 유지합니다. 다음 단계로 넘어가기 전에 검토 결과와 의도적으로 미룬 위험을 기록합니다.

## 3. 통합하고 마무리하기

1. 완료된 단위를 의존성 순서대로 통합하고, 영향받는 단위의 소유자와 인터페이스 불일치를 해결합니다.
2. 집중 검사 전체와 가장 작은 관련 통합·린트·타입·빌드 게이트를 실행합니다. 결함이나 검토 결과로 보장 공백이 드러났다면 회귀 검증을 추가하거나 강화합니다.
3. 보안, 권한 부여, 결제, 데이터 삭제·마이그레이션, 배포 변경은 완료하기 전에 최종 검토자로 보냅니다.
4. 완료된 단위, 실행한 테스트와 결과, 검토 결과·수정 사항, 남은 위험 또는 실행하지 못한 검사를 보고합니다.

## Routing

다음 기본 모델과 추론 수준을 사용합니다. 위임 API가 지원할 때에만 명시적인 모델 재정의를 설정합니다. 위임 API가 Luna route에 Luna를 선택 가능한 모델로 제공하면 Luna를 사용합니다. 위임 API가 Luna를 선택 가능한 모델로 제공하지 않으면 명시된 추론 수준의 Terra를 사용하고, 핸드오프에서 이 대체 사실을 알립니다. 그 밖에 위임 API가 요청한 모델을 제공하지 않는 경우에는 route의 의도와 목적을 달성할 수 있는 모델 중 가장 낮은 사용 가능 모델을 선택하고 핸드오프에서 이를 알립니다.

| 목적 | 기본 모델 | 추론 수준 | 용도 |
| --- | --- | --- | --- |
| 기본 | GPT-5.6 Terra | 높음 | 일반 개발, 분석, 문서화 |
| 아키텍트 | GPT-5.6 Sol | 높음 | 시스템 설계, 기술 선택, 복잡한 구조 |
| 실행자 | GPT-5.6 Luna | 중간 | 작고 명확한 구현 또는 반복 편집 |
| 계획자 | GPT-5.6 Terra | 중간 | 단위 분할, 범위, 실행 순서 |
| 비평가 | GPT-5.6 Terra | 매우 높음 | 요구사항, 논리, 테스트 관점 검토 |
| 심층 문제 해결사 | GPT-5.6 Sol | 매우 높음 | 원인을 알 수 없는 버그, 어려운 리팩터링, 알고리즘 |
| 조사 / 종합 | GPT-5.6 Terra | 높음 | 증거 비교와 결론 도출 |

| 테스트 구현 | GPT-5.6 Terra | 높음 | 단위 / 통합 / 회귀 테스트 |

| 테스트 검토 | GPT-5.6 Terra | 매우 높음 | 보장 공백, 경계 사례, 누락된 검증 |

## 상향 규칙

- 여러 파일·서비스에 걸치거나 원인이 불분명한 실행자 작업은 Terra 높음 또는 그 이상으로 올립니다.
- 보안, 권한 부여, 결제, 데이터 삭제·마이그레이션, 배포 변경에는 최종 검토자를 사용합니다.
- 두 번의 접근이 실패했거나 원인이 여전히 좁혀지지 않았다면 심층 문제 해결사로 올립니다.
- 단순한 작업을 처음부터 매우 높음으로 시작하지 마세요. 낮은 수준에서 시작하고 불확실성이나 품질 위험의 증거가 있을 때에만 올립니다.
- 최종 변경 전에는 필요한 테스트와 검증을 실행합니다. 남은 위험과 검증하지 못한 항목을 명시적으로 적습니다.
